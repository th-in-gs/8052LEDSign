# Signetics SCN8031H ROM Analysis

A second set of 8051-family chips from the same parts drawer. They are marked
as the ROMless 8031, but their 4 KB internal ROM holds a complete program.

Everything this document says about what an address, pin or variable is for
is inferred from how the code uses it.

## Background

The main [`ROM_ANALYSIS.md`](../ROM_ANALYSIS.md) has a fuller introduction to
the 8051 for modern programmers. In brief:

- **Hex** is written `0xFF`. Byte sequences are space-separated hex in code
  font: `C9 64 4A`. The generated listing uses assembler notation (`FFh`).
- **Code addresses** in parentheses, such as (0x0F77), point to the routine
  that does what is being described. They are locations in the ROM and can be
  looked up in `scn8031_annotated.lst`.
- **Internal RAM** is the chip's own 128 bytes of RAM (on this part),
  written as two hex digits: 0x35. Part of it is bit-addressable, and
  `0x20.2` means bit 2 of byte 0x20, used as a flag.
- **Registers** are storage inside the CPU: the accumulator A, B, the working
  registers R0–R7 (four banks of eight, at internal RAM 0x00–0x1F), and the
  special function registers (SFRs) that control the ports, timers and serial
  port.
- **Ports.** The 8051 has four 8-bit I/O ports, P0–P3. Each is 8 pins of
  general-purpose I/O, read and written as one byte, like a GPIO register on
  a modern microcontroller. `P2.5` means bit 5 of port 2, a single pin. P0
  and P2 can instead form an external memory bus, and P3's pins double as
  the serial port (P3.0 RXD, P3.1 TXD), interrupt inputs (P3.2 INT0, P3.3
  INT1), timer inputs (P3.4 T0, P3.5 T1) and bus strobes (P3.6 WR, P3.7 RD).
  This program uses no external memory, so all four ports are free for I/O.
- **Timers 0 and 1** are hardware counters that interrupt the CPU when they
  overflow. Reloading a timer's count (TH0, TH1) sets how often that happens.
  Timer 1 also sets the serial baud rate.

## The chip

Markings:

```
[Signetics logo] 8450
SCN8031H
CCA44  E
```

| Line       | Reading                                                                                       | Confidence |
| ---------- | --------------------------------------------------------------------------------------------- | ---------- |
| `8450`     | Date code: 1984, week 50.                                                                     | Medium     |
| `SCN8031H` | Signetics 8031, HMOS: the ROMless 8051.                                                       | High       |
| `CCA44`    | Ordering-code suffix. `A44` = 44-pin PLCC (the DIP version is `N40`). `CC` = 0–70 °C, 12 MHz. | High       |
| `E`        | Revision or lot letter.                                                                       | Low        |

The program uses ports P0 and P2 as plain I/O and never accesses external
memory, so it was written for an 8051 running from internal ROM. If the part
were truly ROMless, raising EA would have read the external SRAM (the stub
and RAM-test pattern), not a program. The ROM is valid and the program
complete, so the die is functionally an 8051 (SCN8051H): surplus 8051 dies
or a die/package mix-up, marked as 8031s. The top marking is not
trustworthy.

## How it was dumped

With the same circuit and dumper as the OKI MSM83C154 (see the main
`README.md`), in the same PLCC-44 adapter. The board's 13.875 MHz clock is
about 16% above this part's 12 MHz rating, but the dump is coherent. The EA
(External Access) pin selects between internal ROM and external memory. On
NMOS 8051s, EA is generally sampled continuously rather than latched at
reset, which is the basis of the classic 8051 ROM dump. A precedent: the
8051dumper project dumped a Signetics SCN8051H from a Micropolis 1325 disk
drive (DEC RD53-A) this way. That is a different product and program, but
the same die family and EA behaviour.

There is no checksum to verify against: the 8-bit sum is 0x09 and no
checksum routine was found. Instead, the chip was dumped twice and the two
16 KB captures are identical, byte for byte. The code also disassembles
cleanly (3,824 of 4,096 bytes reached as code, 74 called routines).

## What it appears to do: a four-motor positioning controller on a serial bus

### Motors and phase outputs

Four stepper motor outputs, each on four (or three) port pins. Each port is
written through a copy kept in internal RAM, so the other half of the port
is left unchanged. The outputs idle high, so coils appear to be driven
active-low: a 0 bit switches a coil on.

| Motor | Output pins                 | Phase variable            | Next-pattern table | Driven from              | Type              |
| ----- | --------------------------- | ------------------------- | ------------------ | ------------------------ | ----------------- |
| A     | P0.4–P0.7                   | internal 0x43             | 0x04CC             | Timer 0                  | 4-wire, half-step |
| B     | P0.0–P0.2 (P0.3: see below) | internal 0x41             | 0x039A             | Timer 0                  | 3-phase, 6-step   |
| C     | P1.0–P1.3                   | internal 0x11 (bank 2 R1) | 0x04CC             | Timer 1                  | 4-wire, half-step |
| D     | P1.4–P1.7                   | internal 0x0E (bank 1 R6) | 0x04CC             | Motion loop, fixed delay | 4-wire, half-step |

The Timer 0 interrupt steps either motor A or motor B, whichever is moving.
Motor D is stepped by the motion loop itself (0x026C), with a fixed delay
between steps, so it is slow and has no acceleration ramp. An earlier
version of this analysis missed motor D: its output routine (0x0256) writes
the high half of P1, next to motor C.

**Step units differ by motor.** Motor A's counts are multiplied by 3
(0x02AC): one unit is 3 half-steps. Motor B moves 2 steps per carousel
position (0x035E). Motor C and motor D counts are single half-steps. All
motor A figures below are in units unless stated.

**P0.3, motor B's spare line.** The phase table always sets bit 3, so P0.3
is not a coil. It goes low on motor B's last step (0x03B9) and high again
after a delay (0x00CB or 0x0973). Since outputs are active-low, something is
switched on while the carousel settles: extra holding current, a brake or a
detent solenoid.

**Next-pattern tables.** Each step looks up the current 4-bit pattern; the
high 4 bits of the table entry are the next pattern in one direction, the
low 4 bits in the other.

- 0x04CC (motors A, C and D): starting from 0xE, one direction cycles
  E→6→7→5→D→9→B→A→E (hex digits). Inverted (active-low), that is 1, 9, 8, A,
  2, 6, 4, 5: a classic 8-state half-step sequence. Invalid patterns (F, C,
  8, 1 …) lead into the cycle within a couple of steps.
- 0x039A (motor B): uses 3 bits and forces bit 3 high. One direction cycles
  1→3→2→6→4→5→1 (binary 001, 011, 010, 110, 100, 101): 6-step 3-phase
  commutation, for example a 3-phase variable-reluctance stepper. Invalid
  values 0 and 7 recover.
- Both tables overlap code to save space: entries 0–4 and F of 0x04CC are the
  bytes of the instructions at 0x04CC–0x04D0 and 0x04DB, and entries 0 and 7
  of 0x039A are the `RET` at 0x039A and the first byte at 0x03A1. Those
  entries are the invalid patterns, and they still lead back into the cycle.

### What each motor does

- **Motor B: 96-position circular axis.** A target from 0x01 to 0x60 is
  checked at 0x0F77. The firmware takes the difference from the current
  position (internal 0x35); if it is more than 0x30 (48) it goes the other
  way round, 0x60 minus the difference. Shortest-path positioning on a wheel
  or carousel with 96 positions.
- **Motor C: linear axis with tracked position.** A 16-bit position at
  internal 0x36:0x37, kept within 0x0000–0x0C60 (0–3168 half-steps) by
  0x0DF5. Before motor A's actions and when parking, it moves to position
  0x03C0 (960), then returns to a saved position afterwards: probably
  lifting something clear.
- **Motor A: one-way rotary mechanism with a position flag.** The host can
  move it by up to 2047 units (6141 half-steps) in either direction, and the front-panel
  keys jog it. But both of its automatic actions (0xC1 0x04 and 0xC1 0x08)
  turn it the same way and stop relative to the two edges of one sensor
  signal. That pattern suits a cam, crank or rotary valve that always turns
  forward.
- **Motor D: two-position mechanism.** It moves between two states about
  74 half-steps apart, recorded in flag 0x28.2. Every motion command first
  puts it in state 0, and parking puts it in state 1. A lock, clamp or cover
  would fit.

### Homing and position feedback

Open-loop steppers need a known starting point. Each motor gets one
differently:

| Motor | Feedback                                       | Homing                                                        | When                        |
| ----- | ---------------------------------------------- | ------------------------------------------------------------- | --------------------------- |
| C     | Switch on the INT1 pin (P3.3)                  | Two-phase: fast approach to the switch, slow back-off, offset | Every reset (0x0064)        |
| A     | Shift-register input bit 0                     | Stop a fixed distance past a rising or falling edge           | First 0xC1 0x04/0x08 action |
| D     | None for position. P2.5 stops it (fault/limit) | Overdrive against a hard stop, then back off                  | Every reset (0x0F61)        |
| B     | None found                                     | 99 one-position moves while motor C is parked past its switch | Every reset (0x0088)        |

**Motor C** (`motion_init`, 0x0064):
1. Back off 50 half-steps.
2. Drive toward home for up to 3480 (0x0D98) half-steps: more than the 3168
   travel, so it always reaches the switch.
3. Every motor C step reads INT1, twice in a row to debounce (0x044D). INT1
   low sets flag 0x2E.6.
4. When the switch trips, 0x04B3 cuts the remaining count to 36 or 37
   half-steps, keeping the phase, so the motor decelerates rather than
   stopping dead.
5. Creep back 2 half-steps at a time until INT1 goes high again
   (0x0096–0x00A3).
6. Step 12 more half-steps. This point is position 0.

**Motor A** (0x0325 and 0x033B): during every motor A step, the firmware
reads the shift register. With flag 0x2B.0 set it watches for bit 0 going
low; with 0x2B.1 set, for bit 0 going high. When the edge arrives, the rest
of the move is cut to exactly 16 half-steps (not units), using a second
pass if needed.
The two actions that use this:

- **0xC1 0x04** (0x0E46): search up to 576 units (1728 half-steps) for the
  rising edge. Then 16 half-steps, 116 units (348 half-steps), a pulse on
  pin P2.4, then 88 units (264 half-steps). Sets flag 0x2B.2.
- **0xC1 0x08** (0x0E9D): search up to 1318 units (3954 half-steps) for the
  falling edge. Then 16 half-steps and 900 units (2700 half-steps). Clears
  0x2B.2. 0xC1 0x04 runs this first when
  0x2B.2 is set.
- If the edge is not found, error bits are set in the status byte, a fault
  latch (flag 0x23.1) blocks further motion commands, and the carousel parks.

Motor A is not homed at reset. Flag 0x23.0 marks its position as unknown
until an action succeeds, and the main loop reports bit 0 going low as an
error (0x0E29). All of this applies only when the P2.3 option input read
high at reset; otherwise the 0xC1 0x04/0x08 actions are refused. P2.3
probably means "motor A mechanism fitted".

**Motor D** (0x01E8, 0x01EE, 0x01F4, via 0x01FE):
- 0x01E8 moves 96 half-steps towards state 0; 0x01EE moves 74. 0x01F4 moves
  74 towards state 1.
- At reset it runs 96 towards state 0, then 74 back to state 1. 96 is more
  than the normal stroke, so this looks like driving into a hard stop to
  find a reference, then backing off.
- If P2.5 reads low twice in a row during a motor D move (0x027C), the
  remaining count is cut to at most 12 half-steps. A latch (flag 0x23.3)
  then blocks motor D, and status bit 0x29.1 reports it. P2.5 low at any
  time also does this, and aborts the automatic sequence (0x076E). Several
  motor D actions also check that P2.5 is high before starting. So P2.5 low
  means "stop motor D": an end-of-travel, jam or safety input.

**Motor B** has no sensor that the code reads. At reset, `motion_init`
moves it 99 positions, as 99 separate one-position moves of 2 steps each
(0x0088), then sets its position to 1. Some observations:

- 99 positions is just over one revolution of 96. Merely locking the rotor to the
  drive phases would need about 6 steps; a full turn is only needed when
  searching the whole circle for something.
- Short, separate moves are what makes a stepper stall cleanly against an
  obstruction. A 3-phase variable-reluctance motor has no magnet, so
  stalling against a stop does it no harm.
- A **permanent** stop is ruled out: `set_b_target` moves through the 96→1
  wrap (from position 1 to 96 is one step backwards), and the automatic
  sequence moves both ways by uneven amounts. Some legal move would hit any
  fixed stop.
- The 99 moves happen **while motor C is parked 36 half-steps past its home
  switch**, between steps 4 and 5 of motor C's homing. Normal motor C
  positions start after the step 6 offset, so that overtravel zone is
  reached only during homing.

The likeliest explanation is that motor C's carriage, parked in its
overtravel zone, puts an arm or pin into a single notch in the carousel's
path. The carousel turns until the notch meets it and stalls there: position
1. When motor C backs off, the carousel is free to turn either way. That
explains the order of the homing moves, the full revolution, the absence of
a sensor, and why wrap-around moves are safe afterwards. Other explanations
can't be excluded: the carousel may be indexed mechanically by the operator,
for example with a keyed tray. Confidence: high that there is no permanent
stop, low to medium for the motor C arm.

### Parking and control modes

Flag 0x22.6, reported to the host as status bit 0x29.6, marks the machine
as **parked**:

- Parking (`park`, 0x0AE7) moves the carousel to position 1,
  motor C to position 960 and motor D to state 1.
- The machine starts parked after every reset.
- Any accepted 0xC0 command with bit 2 of its second byte clear parks the
  machine (if not already parked). With bit 2 set, it **unparks**: clears
  the flag and returns motor C to its saved position.
- While parked, motion commands and 0xC1 actions are refused, and the
  front-panel jog and action keys work. While unparked, the host has the
  mechanism, and most keys only report to it.

### Automatic sequences

0x0CFD runs one of two automatic sequences, chosen by flag 0x20.2. Pressing
front-panel keys 3 and 4 together while parked starts them. While one runs,
key 2 toggles between them and key 4 stops it, re-homes and restarts.

- **Sweep (0x20.2 set, 0x06F4).** Steps an index between 0x01 and 0x83,
  reversing at each end, moving motor C 0x18 (24) half-steps per index:
  0x83 × 0x18 = 0x0C48, just inside motor C's limit.
- **Scripted carousel sequence (0x20.2 clear, 0x0D05–0x0D5D).** R6 counts
  down from 0x30 (48) on each call while R7 counts up, and motor C moves 0x18
  half-steps per call, its direction flipping each cycle. When R6 runs out,
  the carousel makes a fixed move depending on R7:

  | R7            | Carousel move                                         |
  | ------------- | ----------------------------------------------------- |
  | 1             | 0x26 positions                                        |
  | 2             | 0x10 positions                                        |
  | 0x32          | 0x18 positions                                        |
  | anything else | 0x23 positions back the other way, and R7 resets to 0 |

  R7 peaks at 0x52 (82). Its speed classes come from the table at 0x0FBE
  (see below).

Since a key combination starts them, these are most likely a demonstration
or burn-in mode for service use.

### Speed tables

All step-period ramps go through `ramp_lookup` (0x04ED). It keeps an
acceleration index (R4) that rises by one per step up to the ramp length
(R1), and uses the smaller of it and the steps remaining (R3), so a move
speeds up, cruises and slows down symmetrically. The table entry times a
multiplier (register B) is subtracted from the timer count, so bigger
entries mean longer steps.

- **0x05C5: motor B's ramp,** 29 entries (R1 = 0x1D): `C9 64 4A 3E 36 31 2C
  29 27 24 …` (201, 100, 74, 62, 54 …). It fits about 96/√n + 4, apart from
  the first entry (0xC9), which is an outlier. Step delays proportional to
  1/√n give constant acceleration, the classic stepper ramp.
- **0x05E3: motor B's turnover table,** directly after it: `AC 7E 78 6D 64 …`.
  It is reached by offset: when the acceleration index equals the steps
  remaining, the point where speeding up turns into slowing down, the
  lookup uses index R4 + R1 instead (0x0500). So exactly one step per move
  takes its period from this table, longer for short moves. Only motor B
  does this (the check is on its moving flag, 0x2D.3). The entry at 0x0600
  (0x48) is the period of motor B's last step (0x03BE).
- **0x057D: motor A's ramp,** 13 entries: `98 3F 31 24 … 14`, through
  `ramp_a` (0x031A). Earlier versions called this a motor C ramp.
- **0x01DF–0x01E7: post-move timing for motor B and C moves.** Three 3-byte
  entries, one for each speed class 1–3 (flags 0x2A.0/0x2A.1); class 0 uses
  a fixed delay instead (0x0537). After the last step, `post_move_timing`
  (0x01A6):
  1. sets P3.5 high for class 1 and low for classes 2 and 3;
  2. pulls P2.6 low for one Timer 0 period set by byte 0 (about 4.5–5.4 ms
     at 11.0592 MHz);
  3. marks the mechanism busy.

  Then Timer 0 runs two more periods (0x0EFF, `timer0_alt`): byte 1 (about
  8.3, 5.8 or 4.2 ms), after which P0.3 goes high; then byte 2 (about 16.9,
  8.9 or 8.0 ms), after which the busy flag clears and the next move can
  start. So the speed class also chooses how long the carousel settles
  before the next move: shorter for the faster classes.
- **0x0FBE: carousel sequence speed classes.** Packed 4 to a byte, 2 bits
  each, 100 entries. 0x0F9F indexes it by R7 in the scripted carousel
  sequence (R7 ÷ 4 picks the byte, R7 mod 4 the bit pair) and copies the
  result to flags 0x2A.0/0x2A.1. R7 never exceeds 0x52 there, so the lookup
  stays inside the table (byte index at most 0x14): the table is longer than
  needed. The sweep at 0x06F4 does not use it.
- **0x058A: three-segment period profile for motor C.** Index R5 starts at a
  per-move value (0x04, 0x08, 0x0C, 0x0E, or computed), increments after 12
  steps and again with 7 steps remaining, so each move uses three
  consecutive entries, for example `1C 12 0B` from 0x0E or `32 2A 24` from
  0x04. The entry, multiplied by 0xB0 or 0x40 (flag 0x2E.2), is subtracted
  from the running Timer 1 count, lengthening the step period. R5 = 0x39
  selects 0x00 (no adjustment) and 0x3A selects 0xB7. The long run of
  repeating `1C 12 0B` beyond the used indexes looks like filler. Shift
  register bit 7 selects the 0x04/0x08 starting values (0x0225).

### Inputs

| Input                   | Read at                | Meaning (inferred)                                                                                                                                                        |
| ----------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INT1 pin (P3.3)         | 0x044D, 0x00A0         | Motor C home switch. Low = at home.                                                                                                                                       |
| T0 pin (P3.4)           | 0x0866, 0x0567         | Interlock. Homing waits until it is high; low while unparked, checked during moves, restarts the firmware (re-homing everything). A door, cover or motor-power-OK signal. |
| INT0 pin (P3.2)         | interrupt              | Forces a restart. Also timed during the factory loopback test.                                                                                                            |
| P2.5                    | 0x027C, 0x076E         | Low = stop motor D and report an error.                                                                                                                                   |
| P2.3                    | 0x0F2D, once per reset | Option: motor A mechanism fitted (high).                                                                                                                                  |
| Shift register bit 0    | 0x0325, 0x0E29         | Motor A position flag. Both edges used.                                                                                                                                   |
| Shift register bits 1–6 | 0x053F, 0x0B6F         | Front-panel keys, active-low, debounced over 5 reads.                                                                                                                     |
| Shift register bit 7    | 0x0225                 | Raw (not inverted). Selects a slower motor C start profile. A switch or jumper.                                                                                           |

The shift register is an external parallel-in chip (e.g. a 74x165), read at
0x098A: P2.0 = load, P2.1 = clock, P2.2 = data, 8 bits, most significant
bit first. It turns 8 input lines into a serial stream on 3 pins. The
routine returns bit 0 in the carry flag, copies bit 7 to flag 0x2C.5, and
returns bits 1–6 inverted with bits 0 and 7 cleared.

Front-panel keys (handler 0x0B6F), ignored while the automatic sequence runs
except as described above:

| Key (bit) | Parked                                                             | Unparked |
| --------- | ------------------------------------------------------------------ | -------- |
| 5, 6      | Jog motor A one way / the other, faster while held                 | —        |
| 3 + 4     | Start the automatic sequence                                       | —        |
| 3         | Cycle motor D: 96 to state 0, 74 back to state 1 (needs P2.5 high) | —        |
| 2         | Pulse P2.4, then 88 units (264 half-steps) of motor A              | —        |
| 1         | No host: move motor A 1056 units (3168 half-steps)                 | Same     |
| 4         | —                                                                  | —        |

With a host connected (after the start-up handshake), presses of keys 1–4
are also reported to it: status bit 0x29.2, with the key in byte 0x24. Key
5 jogs with A_DIR clear, key 6 with it set; holding a key repeats the move
with longer steps (0x0601). The gating depends on several more flags; this
table is a simplification.

### Outputs other than motors

- **P0.3:** low from motor B's last step until the settle time ends (see
  "Motors and phase outputs" and the post-move timing).- **P2.4:** pulsed during motor A's 0xC1 0x04 action, between the 116- and
  88-step moves, and by key 2. A signal to other equipment that the
  mechanism has reached a point in its cycle.
- **P2.3:** pulsed at the start of the 0xC1 0x04 action (0x0E59). The same
  pin is read as the option input at reset; 8051 port pins can do both.
- **P2.7:** high while motor C is moving (set at 0x03F0, cleared at 0x045E).
  Perhaps a driver enable or current boost.
- **P2.6:** pulsed low for about 5 ms after a motor B/C move at speed
  classes 1–3 (0x01C7): an "arrived" strobe.
- **P3.5** (normally T1): high after a class 1 move, low after class 2 or 3
  (motor B/C moves).
- **P3.7** (normally RD) and **P3.6** (normally WR, inverted): status from
  the main loop.

### Serial link

- The built-in serial port runs in mode 3 (SCON = 0xD0): 8 data bits plus a
  9th bit, used as a parity bit with selectable sense (flag 0x21.2), checked
  on receive.
- Timer 1 auto-reload, TH1 = 0xFD: 9600 baud if the original crystal was
  11.0592 MHz.
- Frames are 2 bytes. The serial interrupt writes them to internal RAM 0x07
  and 0x06: R7 and R6 of register bank 0, the main loop's working registers.
- At start-up only frames starting 0xC0 are accepted. `C0 80` or `C0 C0` sets
  the parity sense from bit 6, replies, and puts the node into echo mode: the
  next 8 bytes are sent straight back out with the same 9th bit. After that
  the node accepts all frames.
- Every frame gets a 1-byte reply: normally the status byte at internal 0x29,
  or the value requested by a read command.

This looks like a node on a chain or multidrop bus, with a start-up sequence
in which each node echoes traffic before going live.

### Commands

Decoded at 0x0D5E and 0x0B05. First byte (R7), second byte (R6):

| 0x80–0x8F                          | count low                                  | Motor A: move ((R7 bits 0–2) × 256 + R6) units of 3 half-steps, direction R7 bit 3.                                                                                         |
| 0x90–0x9F                          | count low (bit 0 ignored)                  | Motor C: move by ((R7 bits 0–2) × 256 + R6) half-steps, direction R7 bit 3, within the 0–0x0C60 limit.                                                                      |
| 0xA0–0xAF                          | bits 0–6: motor B target                   | Motor B to position R6 (1–0x60), speed class R7 bits 0–1.                                                                                                                   |
| 0xB0–0xBF                          |                                            | Rejected.                                                                                                                                                                   |
| 0xC0                               | 0x00                                       | No other action (see bits 2 and 6 below).                                                                                                                                   |

| 0xC0                               | 0x01                                       | Re-initialise: clear RAM and accept all frames.                                                                                                                             |
| 0xC0                               | 0x02                                       | Leave read mode.                                                                                                                                                            |
| 0xC1                               | 0x40                                       | Enter read mode.                                                                                                                                                            |
| 0xC1                               | 0x20                                       | Motor D to state 1, if not already there.                                                                                                                                   |
| 0xC1                               | 0x10                                       | Park: carousel to position 1, motor C to 960, motor D to state 1.                                                                                                           |
| 0xC1                               | 0x08                                       | Motor A action: to the falling edge of its flag, then 2716 half-steps on. Needs P2.3 high.                                                                                  |
| 0xC1                               | 0x04                                       | Motor A action: to the rising edge, 364 half-steps, pulse P2.4, 264 more. Needs P2.3 high.                                                                                  |
| 0xD0, 0xD1, 0xD2, 0xD4, 0xD8, 0xDE | 0x00                                       | Read a status byte (see "Status bytes"). Reply: the byte itself, not the usual status reply.                                                                                |
| anything else                      |                                            | Rejected: error flags set.                                                                                                                                                  |

For every accepted 0xC0 command, bit 6 of the second byte sets the parity
sense and bit 2 parks (clear) or unparks (set) the machine (0x0A38). So
`C0 00` parks, and `C0 04` hands the mechanism to the host. An earlier
version of this analysis described `C0 00` as doing nothing.

Motion commands (0x00–0xBF) are refused while parked, in read mode, or after
a motor A fault (0x0D6E). Before moving, they put motor D in state 0. The
0xC1 actions other than read mode are refused while parked, in read mode or
after a motor A fault. Moves are refused while another is in progress.

### Status bytes

The node reports status in one byte, and keeps details in five more that
the host reads with the 0xD_ commands (0x0A54).

**The status reply** (internal 0x29). Sent in reply to every command except
the 0xD_ reads, and to a frame that fails its parity check. It is also sent
unprompted when a key is pressed or a fault occurs (main loop, 0x0928).

| Bit | Meaning                                                               |
| --- | --------------------------------------------------------------------- |
| 5   | 1 = reply to a command, 0 = unprompted report                         |
| 1   | Error details waiting in byte 0x23 (read with `D1 00`)                |
| 2   | Key press waiting in byte 0x24 (`D2 00`)                              |
| 3   | Last frame had a parity error and was discarded (detail in byte 0x25) |
| 6   | The machine was parked (by this command, or by a reset)               |

Bits 0, 4 and 7 are always 0. Between reports the byte is reset to 0x20.

**Detail bytes.** All have bit 7 set, and reset to 0x80.

| Command | Byte | Contents                                                                                                                                           | Reading it                                 |
| ------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `D0 00` | 0x22 | Summary. Bit 1, 2, 3 = bytes 0x23, 0x24, 0x25 hold unread news. Bit 5 = ready (cleared while a frame is processed). Bit 6 = parked.                | Sets bit 5                                 |
| `D1 00` | 0x23 | Errors. Bit 0 = motor A flag low or position unknown. Bit 1 = motor A flag edge not found. Bit 3 = P2.5 stopped motor D. Bit 4 = command rejected. | Clears bit 4 and the news bit; faults stay |
| `D2 00` | 0x24 | Keys. Bit 6 = key 1, bit 4 = key 2, bit 3 = key 3, bit 2 = key 4, bit 0 = keys 1 and 4 together.                                                   | Resets to 0x80                             |
| `D4 00` | 0x25 | Communication. Bit 3 = parity error.                                                                                                               | Resets to 0x80                             |
| `D8 00` | 0x26 | Fault code: 0x91 = 0xC1 0x04 action failed, 0xB1 = 0xC1 0x08 action failed.                                                                        | Unchanged                                  |
| `DE 00` | 0x3B | The P2.3 option byte: 0xA5 = fitted, 0xA0 = not.                                                                                                   | Unchanged                                  |

Each read also copies the byte into a snapshot at 0x30–0x34. **Read mode**
(`C1 40`, left with `C0 02`) makes the same 0xD_ commands return the
snapshots instead, without clearing anything. That lets a host fetch a
reply again after a transmission error without losing the information.

The fault bits are latched. Motor A's "edge not found" (bit 1) clears only
on a re-initialise (`C0 01`) or reset. Motor D's (bit 3) clears when key 3
cycles motor D. "Flag low or unknown" (bit 0) clears when the flag reads
high or a 0xC1 0x04 action succeeds.

### Start-up and self-test

- Reset clears internal RAM 0x08–0x42, keeping a few flags, and reads the
  P2.3 option.
- The TXD pin is toggled and the RXD pin watched. If they follow each other
  (a loopback plug), the firmware measures a pulse on the INT0 pin with
  Timer 0, sends 0xAA, 0x00, 0xFE and 0x55, checks each comes back, then
  stops. That looks like a factory test mode.
- Otherwise: all outputs idle, wait for the T0 interlock, home motors C and
  B, then home motor D, move motor C to 960 and start parked.

### Memory layout

Code runs from 0x0000 to 0x07BA, then 0x07BB–0x07FF is unprogrammed (all
0xFF), and code resumes at 0x0800. The program appears to be laid out around
the 8051's 2 KB pages: the short `AJMP`/`ACALL` instructions can only reach
addresses within the same 2 KB block. 0x0FFA–0x0FFE is 0xFF and 0x0FFF is
0x00.

## Possible applications

Everything here is inferred from the code alone: there is no hardware, no
board and no documentation. The firmware controls a 96-position carousel, a
linear axis that parks out of the way, a one-way rotary mechanism with a
position flag and an output pulse, and a two-position mechanism, all
commanded over a serial bus, with a small front panel for jogging and a
demonstration mode. Confidence in that much is moderate to good. Candidates
for the product, most likely first, all low confidence:

1. **HPLC/GC autosampler or sample injector.** The carousel selects one of 96
   vials, the linear axis moves the needle between vial, injection and wash
   positions, and motor A drives a syringe or injection valve through a cam.
   The P2.4 pulse after motor A's cycle would be the "injected, start run"
   signal to the chromatograph. Motor D could be a vial clamp or cover lock,
   released before every move. 96-vial carousels are a standard autosampler
   layout.
2. **Laboratory sample changer, e.g. a gamma counter carousel:** a 96-tube
   carousel, an elevator, a pipettor.
3. **Microplate handler:** possible, but a 96-position carousel suggests vials
   or tubes more than a rectangular plate.
4. **Filter wheel or turret with a scanning stage:** possible, but motor A's
   cam action and the output pulse look more like a sample handler.
5. **Camera pan/tilt head:** unlikely. The 96-position wrap-around axis is too
   instrument-like.

## Relation to the OKI MSM83C154

No evidence that the two were used together:

|                | OKI MSM83C154                             | SCN8031H                                                               |
| -------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| Date           | 1985 or later, probably 1994              | 1984                                                                   |
| Serial format  | 7 data bits + odd parity per channel byte | 8 data bits + parity in the 9th bit                                    |
| Command values | 0x06, 0x07, 0x0B, 0x15, 0x16, 0x20–0x23   | 0x00–0xAF (moves), 0xC0, 0xC1, 0xD0–0xDE                               |
| Function       | Log-scale readings from 8 smart heads     | Four motors: carousel, linear axis, rotary cam, two-position mechanism |

None of the OKI's protocol values appear in this ROM. Functionally, though,
the two are complementary: the OKI looks like a multi-channel measurement
front end and this chip like a sample handler.

A gamma counter is the best joint fit: 6-decade count rates, several
detectors or energy windows, and a 96-tube carousel. An HPLC/GC autosampler
is the best single-unit fit for the Signetics chip alone. The decade-wide
era gap, different serial formats, and absence of cross-references keep the
link speculative.

## Open questions

Not answerable from the code alone:

- What the mechanisms are physically, and what the product is.
- How the carousel (motor B) finds position 1: a stop engaged by motor C's
  overtravel, an operator-indexed tray, or something else.
- What P2.5, the T0 interlock, P0.3 and the P2.3, P2.4, P2.6 and P2.7
  outputs are connected to.
- The original crystal frequency, and so the baud rate and timings.

Still open in the code:

- The full gating of the front-panel keys (flags 0x28.4, 0x28.7, 0x2B.5).
- What flag 0x2C.2 does during motor B's homing.
- Why the first entry of motor B's ramp (0xC9) is an outlier.
- Whether the scripted carousel sequence's move sizes have a pattern.
- Why P2.3 is both an option input and a pulsed output. A jumper pulling it
  low would hide the pulse, so it may really be a bidirectional handshake.
